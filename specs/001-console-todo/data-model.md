# Data Model: In-Memory Python Console Todo App

**Feature**: 001-console-todo
**Date**: 2026-01-02
**Phase**: 1 (Design)

## Purpose

Define the authoritative data model for the Todo domain entity in Phase I. This model MUST remain consistent across all subsequent phases (Phase II-V) per Constitution Principle IV (Domain Model Reusability).

---

## Entity: Todo

### Description

Represents a single task item that users want to track. A Todo captures the essential information needed to describe a task: what it is (title), additional context (description), whether it's done (completion status), when it was created (timestamp), and how to identify it (unique ID).

### Attributes

| Attribute    | Type       | Required | Default        | Description                                                          |
|--------------|------------|----------|----------------|----------------------------------------------------------------------|
| `id`         | `int`      | Yes      | Auto-generated | Unique identifier for the todo. Sequential integer starting from 1. |
| `title`      | `str`      | Yes      | (none)         | Short summary of the task. Cannot be empty or whitespace-only.       |
| `description`| `str`      | No       | `""`           | Additional details about the task. Can be empty.                     |
| `completed`  | `bool`     | No       | `False`        | Completion status. `True` = complete, `False` = incomplete.          |
| `created_at` | `datetime` | No       | Current time   | Timestamp when the todo was created. Used for ordering.              |

### Validation Rules

Derived from specification requirements (FR-001, FR-002, FR-007, FR-012):

1. **ID Uniqueness** (FR-002):
   - `id` MUST be unique across all todos in the system
   - `id` MUST be a positive integer (>= 1)
   - `id` is auto-generated by TodoService, not provided by user

2. **Title Validation** (FR-001, FR-007):
   - `title` MUST NOT be empty string
   - `title` MUST NOT be whitespace-only (e.g., "   ")
   - `title` MUST be trimmed of leading/trailing whitespace before storage
   - Maximum length: Reasonable limit of 200 characters (prevents memory issues per edge case analysis)

3. **Description Validation** (FR-001):
   - `description` is optional (empty string is valid)
   - Maximum length: 1000 characters (prevents abuse, supports edge case "very long description")

4. **Completion Status** (FR-012):
   - `completed` MUST be boolean (`True` or `False`)
   - Defaults to `False` (incomplete) when created
   - Can only transition from `False` → `True` (no "uncomplete" operation in Phase I spec)

5. **Timestamp**:
   - `created_at` is auto-generated at creation time
   - Immutable (never changes after creation)
   - Used for default display ordering (older todos first)

### Python Implementation

**Using Dataclass** (recommended per research.md):

```python
from dataclasses import dataclass, field
from datetime import datetime

@dataclass
class Todo:
    """
    Represents a task item in the todo application.

    Attributes:
        id: Unique identifier (auto-generated)
        title: Task summary (required, non-empty)
        description: Additional task details (optional)
        completed: Completion status (default: False)
        created_at: Creation timestamp (auto-generated)
    """
    id: int
    title: str
    description: str = ""
    completed: bool = False
    created_at: datetime = field(default_factory=datetime.now)

    def __post_init__(self):
        """Validate todo attributes after initialization."""
        # Title validation
        if not self.title or not self.title.strip():
            raise ValueError("Title cannot be empty")

        # Trim title
        self.title = self.title.strip()

        # Length validation
        if len(self.title) > 200:
            raise ValueError("Title cannot exceed 200 characters")

        if len(self.description) > 1000:
            raise ValueError("Description cannot exceed 1000 characters")

    def mark_complete(self) -> None:
        """Mark this todo as complete."""
        self.completed = True

    def is_complete(self) -> bool:
        """Check if todo is complete."""
        return self.completed

    def __str__(self) -> str:
        """Human-readable representation for CLI display."""
        status = "[✓]" if self.completed else "[ ]"
        desc_preview = self.description[:50] + "..." if len(self.description) > 50 else self.description
        return f"{self.id:3d} | {status} | {self.title:30s} | {desc_preview}"
```

### State Transitions

The Todo entity has two states:

```
┌─────────────┐                              ┌─────────────┐
│ Incomplete  │ ──── mark_complete() ───────>│  Complete   │
│ (False)     │                              │  (True)     │
└─────────────┘                              └─────────────┘
     ^                                              │
     │                                              │
     └────────────── new Todo() ────────────────────┘
                   (default state)
```

**Transition Rules**:
- New todos start in "Incomplete" state (`completed=False`)
- `mark_complete()` transitions from "Incomplete" → "Complete"
- No transition from "Complete" → "Incomplete" (not in Phase I spec)
- State is persisted in the `completed` boolean attribute

## Storage Structure

### In-Memory Representation

Per research.md decision, todos are stored in a Python dictionary:

```python
# Type: Dict[int, Todo]
todos = {
    1: Todo(id=1, title="Buy groceries", description="Milk, eggs, bread", completed=False, created_at=...),
    2: Todo(id=2, title="Call dentist", description="", completed=True, created_at=...),
    3: Todo(id=3, title="Finish report", description="Q4 analysis", completed=False, created_at=...)
}
```

**Key**: Todo ID (integer)
**Value**: Todo object

**Rationale**: O(1) lookup by ID for update/delete/mark-complete operations (primary access patterns per user stories).

### ID Generation Algorithm

Sequential integer generation:

```python
def generate_next_id(todos: dict[int, Todo]) -> int:
    """Generate next sequential ID for a new todo."""
    if not todos:
        return 1
    return max(todos.keys()) + 1
```

**Properties**:
- IDs start at 1 (not 0)
- IDs are always increasing
- IDs are NOT reused after deletion (e.g., delete ID 2, next ID is 4)
- Simple and predictable for users

## Relationships

### Phase I (Current)

**No relationships.** Todos are independent entities with no foreign keys or references to other entities.

### Future Phases (Forward Compatibility)

The Todo model is designed to support future relationships without breaking changes:

**Phase II - Web Application**:
- Potential addition: `user_id: int` (foreign key to User table)
- Potential addition: `category_id: Optional[int]` (foreign key to Category table)
- **Migration path**: Add new optional fields with defaults; Phase I code continues to work

**Phase III - AI Chatbot**:
- Potential addition: `priority: int` (1-5 scale inferred by AI)
- Potential addition: `tags: List[str]` (extracted by NLP)
- **Migration path**: Add new fields; existing code ignores them

**Phase IV/V - Kubernetes/Cloud**:
- Potential addition: `version: int` (for optimistic locking in distributed systems)
- **Migration path**: Add versioning field; backward compatible

## Data Constraints Summary

| Constraint               | Rule                                    | Enforcement                  |
|--------------------------|-----------------------------------------|------------------------------|
| ID uniqueness            | Each ID appears exactly once            | TodoService (generator)      |
| ID positivity            | ID >= 1                                 | TodoService (starts at 1)    |
| Title non-empty          | `title.strip()` not empty               | Todo.__post_init__           |
| Title length             | <= 200 characters                       | Todo.__post_init__           |
| Description length       | <= 1000 characters                      | Todo.__post_init__           |
| Completion boolean       | `completed` is `True` or `False`        | Python type system           |
| Timestamp immutability   | `created_at` set once, never modified   | No setter provided           |

## Examples

### Valid Todo Instances

```python
# Minimal valid todo
todo1 = Todo(id=1, title="Buy milk")
# Result: id=1, title="Buy milk", description="", completed=False, created_at=<now>

# Complete todo with all fields
todo2 = Todo(
    id=2,
    title="Finish project report",
    description="Q4 analysis with charts and recommendations",
    completed=False,
    created_at=datetime.now()
)

# Completed todo
todo3 = Todo(id=3, title="Call dentist", description="", completed=True)
```

### Invalid Todo Instances (Raise ValueError)

```python
# Empty title
Todo(id=1, title="")  # ValueError: Title cannot be empty

# Whitespace-only title
Todo(id=2, title="   ")  # ValueError: Title cannot be empty

# Title too long
Todo(id=3, title="x" * 201)  # ValueError: Title cannot exceed 200 characters

# Description too long
Todo(id=4, title="Valid", description="x" * 1001)  # ValueError: Description cannot exceed 1000 characters
```

## Domain Logic Methods

The Todo entity includes minimal domain logic methods:

### mark_complete()

**Purpose**: Transition todo from incomplete → complete state

**Signature**: `def mark_complete(self) -> None`

**Behavior**:
- Sets `self.completed = True`
- Idempotent (calling multiple times has no additional effect)

**Usage**:
```python
todo = Todo(id=1, title="Buy milk")
assert todo.completed == False
todo.mark_complete()
assert todo.completed == True
```

### is_complete()

**Purpose**: Query completion status

**Signature**: `def is_complete(self) -> bool`

**Returns**: `True` if completed, `False` if incomplete

**Usage**:
```python
todo = Todo(id=1, title="Buy milk", completed=True)
if todo.is_complete():
    print("Task is done!")
```

### __str__()

**Purpose**: Human-readable representation for CLI display

**Signature**: `def __str__(self) -> str`

**Format**: `{id:3d} | {status} | {title:30s} | {description_preview}`

**Example Output**:
```
  1 | [ ] | Buy groceries                  | Milk, eggs, bread
  2 | [✓] | Call dentist                   |
```

## Phase Compatibility Notes

### Phase I (Current - Console App)

- Todo model stored in Python dict in memory
- No serialization needed (data lost on exit)
- No database schema

### Phase II (Web App with Persistence)

**Migration Path**:
1. Todo Python class becomes SQLModel model (inherits from both SQLModel and this dataclass structure)
2. Add database-specific fields: `user_id`, `updated_at`, etc.
3. Core fields (id, title, description, completed, created_at) UNCHANGED
4. Phase I code can be reused with minimal changes (import from different module)

**Example Phase II Model**:
```python
from sqlmodel import SQLModel, Field
from datetime import datetime

class Todo(SQLModel, table=True):
    id: int = Field(primary_key=True)
    title: str = Field(max_length=200)
    description: str = Field(default="", max_length=1000)
    completed: bool = Field(default=False)
    created_at: datetime = Field(default_factory=datetime.now)
    user_id: int = Field(foreign_key="user.id")  # NEW in Phase II
```

### Phase III (AI Chatbot)

- AI agent operates on existing Todo model
- No model changes required (AI reads/writes via Phase II API)
- Potential future: add `priority` or `tags` fields inferred by AI

### Phase IV/V (Kubernetes/Cloud)

- Todo model unchanged at domain level
- Infrastructure handles distribution, scaling, event streaming
- Potential: add `version` field for optimistic locking
